# AI 玩 Minecraft 的專案與藍圖格式（2026-11-25，research-scout 兩路查證，主對話整理）

目的：M5（影片 → 藍圖 → 施工）開工前，找出可借鏡的做法。Pokopia 的玩法接近 Minecraft，但我們只有畫面和按鍵，
沒有遊戲 API。標「已讀」的是查證時讀過原文或頁面；標「僅摘要」的只看到摘要或搜尋片段，**不能當依據**。
星數與日期沒有逐頁查證，不列。

## 1. 結論

1. **沒找到只看畫面、又有建築數據的專案。** 有數據的建築 agent 全部靠 Mineflayer API 取得座標並放置方塊。
2. **瓶頸是定位與驗證，不是規劃。** 有 API 時簡單建築成功率可達九成以上；只看畫面的專案明寫站位和定位困難。
3. **模型的空間規劃不可靠。** 不能讓模型一次寫出整個立體結構，也不能讓它自己換算座標軸和朝向。
4. **照藍圖施工有成熟前例**（Baritone）：比對藍圖與現況 → 取差異 → 做一格 → 再比對。
5. **影片直接變藍圖沒有前例。** 幾何重建的做法需要相機參數與高畫質，不適用於社群短片。

## 2. 只看畫面的 agent

- **Cradle（BAAI）**，已讀：[論文](https://arxiv.org/html/2403.03186v3)、[GitHub](https://github.com/BAAI-Agents/Cradle)。
  輸入只有畫面，輸出是鍵鼠，最接近我們的限制。
  - 每一步做 self-reflection：上個動作成功了嗎、任務完成了嗎。
  - 技能是程式函式，入庫前檢查可執行、文件格式、名稱不重複。
  - 記憶：最近 5 筆互動加一份遞迴摘要。
  - 失敗模式：難以精準站到目標前、原地繞圈、GUI 狀態誤判、非寫實美術更難。
  - 數據：Stardew 耕種 4/5、購物 1/5；RDR2 簡單任務 5/5、戰鬥 1/5。
- **Claude Plays Pokémon**，已讀二手整理：[ZenML](https://www.zenml.io/llmops-database/building-and-deploying-a-pokemon-playing-llm-agent-at-anthropic)。
  - 三個工具：按鈕、模型自己管的知識庫、導航器（指定位置後角色自動走過去）。
  - 模型對「我和目標差幾格」的推理弱，所以把導航交給工具。
  - 約每 30 個動作摘要一次對話。
  - 每一步另有從模擬器讀出的位置資料，這部分我們沒有。
- **Gemini Plays Pokémon／Continual Harness**，已讀：[論文](https://arxiv.org/html/2605.09998v1)。
  - 導航技能是技能庫裡收益最大的一類。
  - 事故：一個工具的回覆格式不符，agent 把失敗當成功，同一動作重複 842 次。教訓：成功與否不能由執行者自己說。
  - agent 寫很多記憶、很少讀回。教訓：進度要由程式放進提示，不能靠模型自己去查。
- **PokéAgent Challenge**，已讀前半：[論文](https://arxiv.org/html/2603.15563)。
  - 沒有 harness 的前沿模型完成度約 0%。
  - 明寫用畫面定位（VLM-SLAM）仍是未解問題。
- **ROCKET-1**，已讀：[論文](https://arxiv.org/html/2410.17856v3)。在畫面上指出位置比用語言描述精確。策略本身要大量資料訓練，不適用。
- **不適用，需要訓練或大量資料**（僅摘要）：VPT、STEVE-1、ROCKET-2、Optimus-2／3、OmniJARVIS。
- **僅摘要，未採用細節**：VideoGameBench、GamingAgent、GITM、DEPS、Odyssey、JARVIS-1、Optimus-1。

## 3. 靠 API 的建築 agent（只借上層設計）

- **Voyager**，已讀：[論文](https://arxiv.org/abs/2305.16291)。
  - 技能庫加獨立的 critic（另一個模型實例判斷任務是否達成，最多 4 輪）。
  - 消融：拿掉自我驗證，發現的物品數少 73%。
  - 作者承認 3D 建築的空間錯誤需要人類批評。
- **APT**，一路讀到全文（[HTML](https://arxiv.org/html/2411.17255)），另一路沒抓到內文：
  - 先產出配置摘要，再產出（方塊，座標）清單，最後由 API 執行。
  - 簡單木屋 97.8%、雙層宅邸 81.4%、依參考圖蓋村屋 47.5%。看圖蓋只抓到零件，抓不到立體結構。
- **VoyagerVision**，只讀摘要頁：[論文](https://arxiv.org/abs/2507.00079)。加上截圖回饋；平地約一半成功，失敗集中在複雜結構。

## 4. 模型的空間推理

- **MineAnyBuild**，已讀前半：[論文](https://arxiv.org/html/2505.20148v3)。約 4000 題、13 個模型零樣本。
  - 最高總分 41.02/100（GPT-4o）。
  - 失敗模式：立體位置誤解、文字計畫轉成矩陣時索引或朝向出錯、設計退化成方盒。
  - 論文沒有提緩解方法。
- **Madge & Poesio**，已讀：[論文](https://arxiv.org/html/2407.12734v1)。
  - 不逐步推理時常漏算一個軸，也常把座標系的手性弄反。
  - 逐步推理讓絕對定址從 42.98 升到 76.5，相對定址從 82.02 升到 95.8。
- **VoxelCode**，已讀：[論文](https://arxiv.org/html/2604.02580v1)。寫出可執行的程式遠比寫出空間正確的結果容易。
- **T2BM**，已讀：[論文](https://arxiv.org/html/2406.08751v1)。
  - 用 JSON 當中介：結構件用起點、終點加材質；功能件（門、床）用單點座標加朝向。
  - 模型會寫錯方塊名稱，所以名稱要走受控的對照表。
- 沒找到「逐層文字圖、JSON、程式碼」三種表示法的正面比較。逐層生成是建議，沒有實測支持。

## 5. 藍圖格式與施工工具

- **Sponge Schematic v3**，已讀：[規格](https://github.com/SpongePowered/Schematic-Specification/blob/master/versions/schematic-3.md)。
  - 調色盤加整數網格；調色盤的鍵是「方塊加狀態」，朝向直接寫在裡面。
  - 實體（家具）另外一張表，不混在方塊網格裡。
  - 原點偏移是獨立欄位。
  - 檔案是壓縮的二進位，模型和人都不能直接讀寫，只能當設計參考。
- **Litematic**，已讀 [litemapy 文件](https://litemapy.readthedocs.io/en/latest/litematics.html)。多個命名區域；元資料預存總體積與非空氣方塊數，可當校驗值。
- **Baritone 的 BuilderProcess**，已讀原始碼（由摘要模型轉述）：[原始碼](https://github.com/cabaletta/baritone/blob/master/src/main/java/baritone/process/BuilderProcess.java)。
  - 預設由下往上逐層，本層沒有錯誤位置才進下一層。
  - 反覆重算「與藍圖不符的位置集合」。
  - 到不了或缺料時有降級路徑和明確的暫停狀態，並列出缺的材料。
- **Create 的 Schematicannon**，已讀：[wiki](https://github.com/Creators-of-Create/Create/wiki/Printing-a-Schematic)。缺方塊時暫停並顯示缺什麼，補料後繼續；可設定跳過缺料位置。
- **僅摘要，未採用細節**：Litematica 的圖層模式、材料清單與 verifier；勇者鬥惡龍 創世小玩家 2 的藍圖；各種網頁預覽器。
  預覽器都綁 Minecraft 的貼圖，不認得 Pokopia 的方塊。

## 6. 從影片或圖片重建

- **World2Minecraft**，已讀：[論文](https://arxiv.org/html/2604.27578)。需要每張影像的相機參數，15 個場景仍要人工修正。不適用。
- 沒找到「模型讀影片直接產出方塊結構」的做法或基準。
- 沒找到利用縮時影片中間狀態的做法。
- 「低畫質、鏡頭旋轉的短片不能做幾何重建」是調查員的推論，沒有實測。

## 7. 我們自己的實測（2026-11-25，離線）

`Pokopia-5x5-Larvitar` 影片每秒抽一格，裁掉模糊邊，取 20 格依時間順序給模型，一次問出逐層平面圖。
Opus 5.5 與 Sonnet 5.5 各兩次，共 US$0.19。

| 模型 | 底面 | 層數 | 自評信心 |
| --- | --- | --- | --- |
| Opus 5.5 | 4×5 | 3 | 推測、推測、猜 |
| Opus 5.5 | 5×5 | 4 | 推測、猜、猜、猜 |
| Sonnet 5.5 | 5×4 | 3 | 猜、猜、猜 |
| Sonnet 5.5 | 5×4 | 3 | 推測、猜、猜 |

- 影片標題寫 5×5，四次只有一次答對。
- 任兩份結果裡「至少一份有方塊」的格子，45% 到 66% 相同。
- 四份都抓到大致結構（石塊底座、中間泥土地、後方高牆、前方階梯），也都知道自己在猜。
- 這只是一種問法：沒有逐層分開問，沒有對照預覽圖自查。
- 現有的 M4 錄影是除錯過程（選單、放了又拆、最多 4 塊），不適合當有標準答案的測試影片。
